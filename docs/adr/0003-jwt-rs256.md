# ADR-0003 — Entrega de la clave pública JWT

| Campo | Valor |
|---|---|
| Estado | Propuesto |
| Fecha | 2026-11-10 |
| Decisores | Equipo, responsable de seguridad |
| Relacionados | CU-01 a CU-04, [`security.md`](../security.md), [`architecture.md`](../architecture.md) |

## Contexto

`security-service` emite tokens **JWT RS256**. El gateway y los servicios Node.js deben validar la firma con la clave pública. La clave privada nunca sale de `security-service`.

El backend ya tiene instalado `jose`, que soporta claves PEM, JWK y JWKS. Falta decidir **cómo recibe la clave pública** cada componente, especialmente en Docker y en el despliegue.

## Decisión

**Pendiente de aprobación.** Se proponen tres opciones; la elección debe registrarse aquí antes de implementar autenticación real.

### Opción A — Clave pública en variable de entorno

`JWT_PUBLIC_KEY` contiene la clave PEM o su representación base64. Cada servicio la lee al arrancar.

| Ventajas | Desventajas |
|---|---|
| Simple y compatible con Docker y CI | La rotación exige reiniciar los servicios |
| No requiere red ni archivos montados | La variable puede ser grande y difícil de manejar |
| Funciona igual en local y producción | Riesgo de exponerla en logs si se imprime la configuración |

### Opción B — Archivo montado

La clave pública vive en un archivo de solo lectura montado en cada contenedor.

| Ventajas | Desventajas |
|---|---|
| No depende del tamaño de una variable | Requiere gestionar volúmenes y permisos |
| La rotación puede hacerse reemplazando el archivo | Hay que reiniciar o recargar el servicio |
| Más fácil de auditar que una variable | Complica el entorno local si no hay Docker |

### Opción C — Endpoint JWKS

`security-service` publica `/.well-known/jwks.json` y los servicios obtienen y cachean las claves.

| Ventajas | Desventajas |
|---|---|
| Rotación de claves sin reiniciar | Más complejidad y una llamada de red adicional |
| Estándar y compatible con `jose` | Hay que cachear y manejar fallos del endpoint |
| Escala mejor si hay varias claves | Requiere que el endpoint sea accesible internamente |

## Recomendación

- **Para la beta:** Opción A o B, por simplicidad.
- **Si el tiempo alcanza:** Opción C, porque permite rotación real.
- La opción elegida debe aplicarse igual en gateway y servicios.
- La clave privada solo debe existir en `security-service`.

## Consecuencias

- El backend no debe generar ni firmar tokens; solo validarlos.
- La clave pública no es un secreto, pero debe gestionarse con cuidado.
- La rotación de claves debe documentarse en `deployment.md`.
- Los tests deben cubrir token válido, expirado, con firma inválida y con `alg` incorrecto.

## Pendientes

- Aprobar la opción.
- Definir el nombre exacto de la variable o la ruta del archivo.
- Definir el procedimiento de rotación.
- Confirmar si `security-service` expondrá JWKS.

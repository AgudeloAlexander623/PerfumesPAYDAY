# ADR-0003 — Entrega de la clave pública JWT

|---|---|

## Contexto

`security-service` emite tokens **JWT RS256**. El gateway y los servicios Node.js deben validar la firma con la clave pública. La clave privada nunca sale de `security-service`.

El backend ya tiene instalado `jose`, que soporta claves PEM, JWK y JWKS. Hace falta decidir **cómo recibe la clave pública** cada componente, especialmente en Docker y en el despliegue, y cómo se rota sin invalidar sesiones activas.

## Decisión

Se adopta la **Opción C (JWKS) como mecanismo principal** y la **Opción A (clave pública por entorno) como respaldo** para desarrollo local, pruebas y entornos sin resolución de nombres internos.

### 1. Fuente de la clave

| Entorno | Fuente | Variable |
|---|---|---|
| Docker y producción | JWKS de `security-service` | `JWT_JWKS_URL=http://security:8000/.well-known/jwks.json` |
| Local y pruebas | Clave pública en entorno | `JWT_PUBLIC_KEY` en PEM o base64 |
| Pruebas unitarias | Clave efímera generada por el test | `JWT_PUBLIC_KEY` |

Reglas:

- Cada servicio configura **una sola fuente**. Si están `JWT_PUBLIC_KEY` y `JWT_JWKS_URL`, el servicio no arranca.
- En producción, si no hay ninguna fuente, el servicio no arranca. En desarrollo se registran los guards y las rutas protegidas responden `401`.
- La clave privada solo existe en `security-service`; nunca se copia al gateway ni a `catalog`/`orders`.

### 2. Validación

- Algoritmo permitido: **RS256 exclusivamente**. Se rechazan `none`, `HS256` y cualquier otro algoritmo.
- El verificador usa el `kid` del encabezado para seleccionar la clave del JWKS.
- El JWKS solo publica `kty`, `n`, `e`, `kid`, `alg` y `use`; `alg` debe ser `RS256` y `use` debe ser `sig`.
- Tamaño mínimo de clave: **2048 bits**; se recomienda 3072 bits.
- El `kid` se deriva de la huella JWK (RFC 7638) o de un identificador versionado explícito. Debe ser único.
- Se validan `iss`, `aud`, `exp` y `iat`; la tolerancia de reloj es de 5 segundos.
- Se exige `typ: "access"` en el payload para que un token de otro tipo no se acepte como access token.

### 3. Rotación

- `security-service` firma con la clave **activa** y publica en el JWKS la clave activa y la anterior durante una ventana de solape.
- La ventana de solape debe cubrir al menos la vida del access token (15 minutos) más la tolerancia de reloj; se recomienda **24 horas**.
- Después de la ventana, la clave anterior se retira del JWKS y se destruye de forma segura.
- El caché del JWKS en Node es de **5 minutos** como máximo y el *cooldown* ante errores es de **30 segundos**.
- Si llega un `kid` desconocido, el verificador refresca el JWKS una vez antes de rechazar el token.
- La rotación es una operación administrativa documentada; no se hace en cada arranque.

> La implementación actual soporta JWKS y clave PEM, pero con una sola clave activa. La rotación con solape y el refresco ante `kid` desconocido se implementan en la Fase 4 del plan de autenticación.

### 4. Fallos y observabilidad

- Si el JWKS no responde, el gateway responde `503` con `UPSTREAM_UNAVAILABLE`; no debe confundir una dependencia caída con un token inválido.
- Un token con firma, `iss`, `aud`, `exp` o `typ` inválidos responde `401` con `WWW-Authenticate: Bearer`.
- Los errores de validación no revelan qué claim falló al cliente; el detalle queda en logs correlacionados por `requestId`.
- Nunca se registran claves, tokens ni cookies en logs.

### 5. Configuración

```text
# Gateway, catalog y orders
JWT_ISSUER=perfumesgold-security
JWT_AUDIENCE=perfumesgold-api
JWT_JWKS_URL=http://security:8000/.well-known/jwks.json
# Alternativa local:
# JWT_PUBLIC_KEY=base64_del_PEM_SPKI
```

En Docker Compose se prefiere `JWT_JWKS_URL`; `JWT_PUBLIC_KEY` queda para ejecución local y pruebas.

## Alternativas consideradas

| Alternativa | Ventajas | Desventajas | Veredicto |
|---|---|---|---|
| A — Clave pública en variable de entorno | Simple, sin red, funciona en CI | Rotación exige reiniciar; variable grande | Aceptada como respaldo |
| B — Archivo montado | No depende del tamaño de la variable; auditable | Requiere volúmenes y permisos; reinicio para recargar | Descartada para la beta |
| C — Endpoint JWKS | Rotación sin reiniciar; estándar; varias claves | Una llamada de red y caché que gestionar | **Aceptada como principal** |

## Consecuencias

- El backend no genera ni firma tokens; solo valida.
- La clave pública no es un secreto, pero debe gestionarse con cuidado.
- El despliegue necesita que `security-service` esté sano antes de que el gateway empiece a validar.
- La rotación de claves requiere soporte de múltiples claves en el emisor y en el JWKS.
- Los tests deben cubrir token válido, expirado, firma inválida, `alg` incorrecto, `kid` desconocido y JWKS no disponible.
